# ADR 0004: 接続所有権と既存ブランチの引き継ぎ

- 状態: Accepted
- 日付: 2026-08-13

## 背景

複数のローカル`serve`から一つのJobを再開できる一方、同じJobまたはcanonicalブランチを二つのworkerが同時に変更してはならない。[ADR 0002](./0002-job-ownership-and-execution-state.md)はJob leaseとbranch lockを要求したが、その記録を置く場所を未決定としていた。

所有権や操作履歴のためにGitへ専用ブランチ、タグ、参照、コミットメタデータを追加すると、ソースコードとチェックポイント以外の運転データをリポジトリへ持ち込む。GitHub IssueやLinear issueの通常の更新には、二つの`serve`が同時に所有権を取得することを防ぐ原子的な比較更新がない。GitHubも、書き込み要求の条件付き更新は個別に明記された機能を除いて対応しないとしている（[GitHub REST APIの推奨事項](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)）。公開リレーのDurable ObjectsストレージへJobデータベースを置くことも、リレーを通知、経路制御、認証情報境界に留める方針へ反する。

既存ブランチを引き継ぐために過去の各送信を証明しようとすると、同じ問題を操作台帳へ移す。コード変更は最終的にプルリクエストで人間が承認し、worktree backendはリポジトリのコード自体を信頼境界の外に置かない。したがって、過去の書き込み証明ではなく、現在のGit差分を未検証の作業途中成果として再検証する。

## 決定

### 保存境界

Gitにはソースコード、通常の作業ブランチ、チェックポイントコミットだけを置く。所有権、排他、操作履歴を保存する専用ブランチ、タグ、参照、コミットメタデータ、検査結果台帳を作らない。

公開リレーは所有権記録、ブランチ排他記録、Jobデータベース、所有権履歴をDurable Objectsストレージへ保存しない。既存のデバイス登録簿と経路制御情報以外の永続データを増やさない。詳細な操作記録、送信待ち記録、実行履歴は各`serve`のローカルSQLiteだけに保存する。

### 接続所有権

Job leaseとbranch lockは、公開リレーへの有効な接続付随情報を持つ専用WebSocket接続として表す。認証、生存確認、失効、再接続の詳細は[ADR 0005](./0005-connection-liveness-and-external-write-reconciliation.md)を正本とする。

- Job識別子をキーとするJob所有権接続は同時に一つだけ存在できる。
- リポジトリ識別子とcanonicalブランチをキーとするブランチ排他接続は同時に一つだけ存在できる。
- 対話JobはJob所有権だけ、実装JobとPR対応JobはJob所有権を先に取得してからブランチ排他も取得する。
- 各取得にはリレーが不透明な取得IDを割り当てる。取得IDは接続中の現在所有権を照合する値であり、履歴や通し番号ではない。
- Durable ObjectはHibernation APIの接続付随情報から、接続中のキー、所有者、取得IDを再構成する。接続付随情報は休止を越えて維持され、接続が閉じると失われる（[Cloudflare WebSocket Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)）。その時点で所有権も存在しない。
- 明示的な解放はブランチ排他接続、Job所有権接続の順に閉じる。予期しない切断では両方が失われたものとしてworkerを止める。

Durable Objectは同じリポジトリに対する取得要求を一つずつ処理し、外部の入出力を挟まずに既存接続を確認してから新しい接続を受理する。取得結果を`serve`が接続越しに読み返すまでworkerを開始しない。

### 外部操作前の確認

`serve`は外部操作の直前に、必要な所有権接続を通じてリレーへ確認要求を送り、期待するJob識別子、canonicalブランチ、取得IDが現在接続と一致する応答を受けた場合だけ操作を送信する。確認不能、接続断、取得ID不一致では新しい外部操作を送らず、workerを停止して`interrupted`へ移る。

確認応答とGitHubまたはLinearの書き込みは原子的にはできない。確認後に接続を失い、古い書き込みが遅れて反映される可能性は残る。外部書き込みは可能な場合に現在値の比較条件を使い、結果不明では盲目的に再送しない。新しい所有者が予期しないブランチ先端の変更を観測した場合はworkerと外部操作を止め、現在状態と接続所有権を再調停する。安全条件が再び揃えば、変更後の先端を未検証の作業途中成果として検査と修復をやり直す。

有効な接続の存在を確認できない間は引き継がない。接続断の検出時間をplatform保証として推測せず、リレーが旧所有権接続の消失またはheartbeat不成立による失効を確認した後だけ新しい接続を受理する。この判断は安全性を可用性より優先する。

### 実装ブランチの再開

人間がTriageからTodoへ再承認した時に承認指紋が同じ場合、同じ論理Jobとcanonicalブランチを再利用する候補になる。既存ブランチの過去の送信が信頼された`serve`による既知の書き込みだったことや、安全なチェックポイントだったことを永続記録から証明しない。

次をすべて満たす場合だけ、引き継ぎ先`serve`が既存ブランチを引き継ぐ。

1. GitHub Issue、Linear issue、その関連付け、承認指紋が現在値から一意に再構成できる。
2. 承認指紋から導出したcanonicalブランチが一意に存在し、先端を読める。
3. 実装Jobのプルリクエストがまだ存在しない。実装中はプルリクエストを作らない。
4. 先行するJob所有権接続とブランチ排他接続が存在しない。
5. 引き継ぎ先`serve`が自分のJob所有権とブランチ排他を取得し、現在の取得IDを読み返せる。
6. 所有権取得後にGitHub、Linear、Gitを再読し、承認対象、承認指紋、ブランチ名、先端が先行する読み取りと一致する。

構造検査を通ったブランチ先端は、正しい完成物ではなく未検証の作業途中成果として扱う。引き継ぎ先workerは差分を読み、リポジトリの検証手順を最初から実行する。ビルドまたはテストの失敗は引き継ぎ自体を拒否する理由にせず、同じ承認範囲で修復する。承認対象、所有権、ブランチ対応、Git履歴を現在値から一意に再構成できない場合だけ安全側で停止する。

ローカル実行履歴や過去の操作記録を利用できれば診断と作業文脈の復元に使ってよいが、引き継ぎの必須条件または正本にはしない。

### 取り込み先ブランチの前進とプルリクエスト作成時機

canonicalブランチの初回作成中は、[ADR 0003](./0003-approval-admission-and-reconciliation.md)の原子的なGit参照作成が確認した取り込み先ブランチのOIDを比較条件にする。canonicalブランチ作成後に同じ取り込み先ブランチが前進しても、WHATまたはHOWの変更ではないため承認指紋とJobを失効させない。同じworkerまたは引き継ぎ先workerがリポジトリの方針に従って最新の取り込み先ブランチを統合し、ビルドとテストをやり直す。

実装中は下書きを含むプルリクエストを作らない。実装と検証が完了し、チェックポイント専用のHANDOFFを最終差分から削除した後に、レビュー可能なプルリクエストを初めて作る。プルリクエスト作成後のレビュー、必須検査の失敗、追加修正は実装JobではなくPR対応Jobが扱う。

## 帰結

- Gitはソースコードとチェックポイントの履歴に留まり、運転データの保存場所にならない。
- リレーは実行割当機能やJobデータベースにならないが、接続中だけ有効な所有権の排他調停を担う。
- 接続断では実行を継続できず、旧接続の消失を確認するまで引き継げない。
- ローカル状態を失っても、GitHub、Linear、Gitの現在値と新しい接続所有権から同じJobを再構成できる。
- 既存ブランチの由来を証明する代わりに、現在の差分を未検証として再検証する費用を受け入れる。
- 実装中の進捗はチェックポイントブランチで共有し、プルリクエストは実装結果が人間の最終承認へ進める状態になってから作る。

## 対象外

- デバイス登録と所有権取得messageの最終的なwire field
- heartbeatの具体的な時間値
- ビルド、テスト、再試行、資源制限の運用値

## 実装前の検証

接続所有権を有効にする前に、Durable Objectsの休止後に接続付随情報から所有権を復元できること、同じキーへの同時取得が一つだけ成功すること、明示解放、接続断、heartbeat不成立で所有権が消えること、外部操作前の確認が失効後に失敗することを検証専用環境で確認する。

既存ブランチ引き継ぎは、同じ承認指紋、先行接続の消失、同時引き継ぎ、取り込み先ブランチの前進、ビルド・テスト失敗、予期しない遅延送信をテスト専用環境で検証する。
