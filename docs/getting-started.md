# 最初の作業を完了する

OrielはGitHub Issueを要求（WHAT）、Linearの課題を実装計画（HOW）、GitHubのPRを変更の確認に使います。端末の`orield`がCodexを実行し、Web画面と中継サービス（Relay）が操作と認証を担当します。

## 準備

- Linux x86_64、Rust stable、Gitを用意します。公開時の検証環境はUbuntu x86_64です。
- `codex`を導入して認証し、対象端末で実行できることを確認します。自動実装には`auto_review`対応版が必要です。`auto_review`は、Codexが実行要求を審査する方式です。
- OrielのWeb・Relayが稼働していることを確認します。`orield`の導入にサービスの配備は含まれません。
- 対象リポジトリをGitで取得し、`origin`がGitHubのリポジトリを指すことを確認します。GitHub Appの導入・アクセス許可と、Linearの接続・承認を行えるアカウントを使います。

公開済みの版を使う場合は`cargo install orield --locked --version '=0.1.0'`を実行します。公開前やソースから導入する場合は、Orielの取得先で`cargo install --path crates/orield --locked`を実行します。`orield --help`で起動を確認します。[公開担当者向け手順](orield-release.md)は配布物の検証・公開に使います。

## 端末を登録する

1. 作業するリポジトリへ移動し、`orield workflow`を実行します。WHATとHOWの確認を続けるコマンドです。
2. 初回起動時に表示されるリンクをWeb画面で開きます。パスキーでアカウントを作成するかログインします。パスキーは端末の認証機能を使うログイン手段です。
3. Web画面で端末名と端末IDを確認し、自分の端末を承認します。
4. 端末に表示されたアカウント名とIDを確認して`yes`を入力します。Webの端末一覧に登録完了が表示されることを確認します。`workflow`や`codex`で起動した端末は、端末中継が未接続でも登録できます。

登録リンクには期限があります。期限切れ・取消し時は端末で登録をやり直します。未確認登録はRelay全体で1024件までです。期限切れの端末IDは元のホスト秘密値の予約として残り、同じ端末の再試行を認めます。上限時は既存登録の確認か端末からの取消しで枠を空けます。認証ファイルを削除して別の端末として再試行しないでください。

## GitHubとLinearを接続する

Webの「設定」を開き、GitHub連携を開始します。認証画面で許可し、対象リポジトリを選んで保存します。GitHub Appが対象リポジトリへアクセスできることも確認します。続いてLinearを認証し、HOWを置くチームを選んで保存します。対象端末のリポジトリと、選択したGitHubリポジトリを一致させます。`orield integrations`でも接続状況を確認できます。

Linearの対象チームでTriageを有効にします。Triageは計画を人が確認するための未承認状態です。Todoは実装の承認、In Progressは実行中、Doneはマージ後の完了反映に使います。同名状態が複数ある場合や、必要な状態がない場合は、Webの停止理由に従ってチームの状態設定を確認します。

## 対象リポジトリで実行を許可する

[設定例](../.oriel.example.yaml)を対象リポジトリの`.oriel.yaml`として保存します。検証コマンドを対象プロジェクトに合わせて変更し、GitHubの既定ブランチへコミットします。計画作成はこの実行許可がなくても利用できます。

| 項目 | 意味 |
| --- | --- |
| `schemaVersion: 1` | 設定形式の番号 |
| `execution.backend: worktree` | Gitの作業ツリーを分離して変更を作る |
| `execution.autonomous: true` | 人のTodo承認後に自動実装を認める |
| `execution.verification` | 公開前に端末が実行する検証コマンドの配列。1件以上必要 |

検証コマンドは引数ごとの配列で指定します。`["cargo", "test"]`はシェル文字列ではありません。`&&`などは解釈されません。検証は対象の変更を確認し、追跡済みファイルや無視対象でないファイルを書き換えないものにします。認証情報を設定へ書かないでください。設定例はRustプロジェクト向けなので、別の言語ではそのプロジェクトの試験コマンドへ置き換えます。

設定は対象コミットから読み取られます。手元でファイルを作るだけでは有効になりません。未知の設定項目、`modelCapabilities`による未検証の能力宣言、プロジェクト内の実行用Codex設定などは拒否されます。

## WHATから完了まで

1. Webのワークフロー画面で端末を選び、「作業を作成」からWHATをGitHub Issueに登録します。タイトルは256文字、本文は60000文字までです。絵文字などは2文字分になる場合があります。既存Issueも使えます。
2. 対象Issueで、人が`/oriel how`で始まるコメントを投稿します。例は`/oriel how 導入手順を更新する計画を作成してください`です。コメントがない間は「計画依頼待ち」です。
3. `orield workflow`を起動したまま待ちます。HOWがLinearのTriageに作成され、Issueへの正式リンクが付くことを確認します。
4. Webの作業詳細からHOWを開き、範囲・手順・検証方法を確認します。変更が必要ならTriageのまま相談します。内容を承認するときは、人がLinearの課題をTodoへ移します。Issue作成や計画依頼だけでは実装を承認しません。
5. 端末が外部状態と実行設定を再確認し、実装と設定した検証を実行します。Webで進捗と検証対象コミットを確認します。詳細の「実行履歴」では、再読み込み後も[保存した実行の経過](execution-history.md)を確認できます。文書だけの変更も、検証後にPRを作成できます。
6. 「レビュー待ち」になったらGitHubでPRを確認します。端末側の検証とGitHubのCIは別の確認です。CIはGitHub上の自動検証を指し、未取得・検査なしを成功として扱いません。修正依頼はPRで`/oriel`から始めるコメントを使えます。
7. 人がPRをマージします。端末がマージを確認してLinearをDoneへ移し、Webの完了表示を確認します。確認前に端末を終了した場合は、再起動か`orield workflow --once`で再確認します。

HOWの内容やWHATが承認後に変わると、旧承認では続行できません。Triageへ戻して内容を確認し、人がTodoで再承認します。PRのマージ競合は承認済みの範囲で解消を試み、検証後に同じPRへ反映します。

## 停止と確認先

Webの「設定」でブラウザー通知を有効にすると、画面を開いている間の承認待ち・レビュー待ち・停止を通知します。初回表示では通知の許可を要求しません。無効化も同じ設定から行えます。

WebのCodex画面で一時停止すると、実行中の子プロセスを停止し、作業を保持します。再開操作では定期確認の時刻を待たずに状態を取り直します。Todo承認と実行設定は再確認します。端末でのCtrl-Cはデーモンを終了します。再起動には対象リポジトリで`orield workflow`を実行します。`--once`は1回だけ確認・処理し、作業失敗時は終了コードを非0にします。

| 表示・症状 | 確認する場所 |
| --- | --- |
| 計画依頼待ち | 対象Issueに人の`/oriel how`コメントがあるか |
| 承認待ち・実行不可 | LinearのTriage/Todoと既定ブランチの`.oriel.yaml` |
| 連携未接続・失効 | Webの設定。対象リポジトリ・チームとサービス側のアクセス許可 |
| 進捗が未確認 | 端末の`orield workflow`の起動状態と通信。切断だけでは成功・失敗を確定しない |
| Codex接続不可 | 端末でCodexが実行できるか。相談サービス終了後はworkflowを停止して起動し直す |
| 検証失敗・人の判断が必要 | Webの停止理由、端末の表示、保存された作業と検証ログ |

端末の認証情報・作業・ログの保存先は[orieldの設定と保存先](../crates/orield/README.md#設定と保存先)を参照してください。認証ファイル、会話、端末出力をIssueやREADMEへ貼らないでください。Web・Relayの配備・検証は[開発手順](../README.md#開発する)、公開は[公開手順](orield-release.md)を参照してください。

## 手順の検証範囲

コマンドのヘルプ、設定例を現在の解析処理で受理すること、端末登録と外部連携・承認の模擬試験を確認しています。実アカウントでの認証、公開版の取得、本番での初回作業とマージには、稼働中のWeb・Relay、対象サービスの許可、Codexの認証が必要です。この手順の検証では本番の作業や配備を作成しません。
